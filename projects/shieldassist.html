生产可靠性

独立负责生产可靠性。两个月，29 个合并 PR，把精度、可靠性、安全一条线管到底。

角色 AI 应用开发实习生 · 独立负责生产可靠性 技术栈 Python · LangGraph · MySQL · Gateway

起点

7 月 3 日入职。第一周在排一个深坑：数据库迁移只建了 38/56 张表，gateway 一启动就 panic（issue #16）。彼时系统没有人对它当前的状态负责。

于是我的工作从「修 bug」变成「先让这个系统值得被修」：把所有问题立案、编号、排优先级，然后一条一条闭环。下面四条证据链，就是这个方法跑两个月的结果。

四条证据链

链 A · 精度病根 从诊断到验证的闭环

issue #24 立案两大线上精度问题 → PR #29 病根①否定检测：原信号匹配用 strings.Contains，「我從沒投資過」被误判为投资诈骗；抽出纯函数后，命中信号词再检查前方窗口内有无否定词，否定词清单刻意克制（排除「非」防误伤「非官方」，排除裸 no 防「note」），另一候选方案经调查后主动撤销，取舍完整留在 PR 正文 → PR #30 病根②报告可观测性 + 重试 + 分层模式 → 8 月底生产对照：AI 写作率 0% → 87%（口径已修正）。

链 B · 8 月 7 日可靠性日 一个根因，四连发

issue #34 行动报告卡转圈：runId 漂移致前端无限轮询。同日 PR #35 修漂移、#36 fraud_fact 与 action_report 并发（100s → 25s）、#37 轮询 3 分钟超时兜底、#38 结构化输出重试链异常分层（防 3 倍延迟放大）。一天之内，一个根因 issue 加四个修复与优化 PR。

链 C · 两次线上事故 两次闭环

issue #51 浏览器自动翻译致立案向导整页崩溃 → PR #52 禁译 + 全局错误页 P0 上报 + 自动恢复（止血发版生产）。issue #59 同签名二次 crash：注册页揭码瞬间崩溃，第一批修复的覆盖缺口 → PR #60 登录页退出翻译 + 表单区局部错误边界。事故正式 issue 化，边界被第二批补全。

链 D · 全量安全审计 发现 → 确证 → 立案 → 跟踪

PR #46 19 份审计文档：API 底册（Gateway / gRPC / 工作流引擎 / OCR / Speech 各域路由全量登记）+ 逐操作四问矩阵 + file:line 级证据。高危发现全部正式 issue 立案，带编号、带证据、带修复批次，推动多项高危问题修复；待裁决项整理成清单推动决策，P0 只写到类别级，利用路径不上公网。
